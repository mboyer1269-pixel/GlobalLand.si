# Private inquiry execution and delivery

## Approved intent

The founder approved the next priority on 4 November: private request -> actual work -> useful deliverable -> reply in the same thread, with durable recovery and no duplicate execution/send. The preceding commercial plan already specifies a private work ledger rather than the public WORLD queue. Markets and methods remain agent choices; no sale, payment or outreach is authorized or implied.

## Approach

Extend the existing Python mail cycle with a private case responder, reusing the subscribed Controller planning interface and installed isolated executor. This is the implementation choice for the approved increment. Putting customer tasks through Supervisor.execute_tool would publish their requests/results; it is unsuitable. Adding a second external workflow service would require another account before the installed stack is used.

Each inbox/message identity maps to one private case. Persist the inbound snapshot, model-selected tasks, execution receipts, output hashes and final response under state/private. The public projection contains aggregate counts only. Do not add case paths, subjects, addresses, requests or artifacts to Git/public WORLD. Follow-up mail is a separate case bound to its inbound message and recorded provider thread; do not infer customer identity solely from a claimed thread.

The correspondence model may answer/ignore, choose EXEC work, inspect results, revise unsuccessful work and select actual generated UTF-8 files for delivery. Execution uses the existing no-network Docker sandbox with pinned image, no host secrets and only this case's input plus bounded public product context. The execution path must never invoke public publication. A model assertion is not an execution receipt. Supply receipts back to subsequent planning; do not claim output was validated independently unless it was.

Public-source retrieval can be included only through the existing validated public GET helper, for exact URLs already provided in this message/public context; never pass arbitrary generated private content into a URL. General browsing, inbound attachments and new paid services are outside this increment; report these limits honestly. The agent retains arbitrary code choice within the existing isolated executor.

Final delivery uses the existing reply endpoint and original inbound identity. Prefer bounded UTF-8 file attachments if the official API contract is confirmed; otherwise deliver exact file text inline with filename/hash. No recipient chosen by the model. The host adds AI disclosure. A durable READY response survives failures before send. Existing STARTED -> UNKNOWN protections remain; UNKNOWN is never automatically resent. API acceptance is not recipient delivery.

## Recovery and scheduling

Persist work before execution and its result before planning again. A crash around isolated computation can be retried only with proof the previous sandbox has stopped (no network effects); alternatively preserve an explicit uncertain work state and let the agent see that it cannot claim success. Never silently rerun a completed operation. Bound work per cycle to preserve normal agents' progress; deferred cases remain retryable. Invalid/missing/corrupt paths fail with fixed non-private errors. Cases and artifacts are isolated from one another and owner-only outside the disposable sandbox mount.

## Acceptance

1. A controlled request makes the model choose a program, actually execute it, inspect the receipt and deliver the generated result in the original thread.
2. A repeat cycle neither reruns completed work nor sends twice.
3. Failure after computation but before send reuses the stored output; uncertain sends stay UNKNOWN.
4. Path traversal/symlink/cross-case access, unsupported public actions, unexpected recipients and invented filenames are rejected.
5. Public status contains no customer text or identifiers; normal existing mail behavior remains compatible when fulfillment is disabled.
6. Run deterministic tests and a real sandbox check, then a controlled real email test. Report spam intervention, provider limitations and test-vs-customer status separately.
